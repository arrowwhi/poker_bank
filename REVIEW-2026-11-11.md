Объект: весь репозиторий (Go-бэкенд, Telegram-бот, HTTP API Mini App, webapp, миграции, инфраструктура, ТЗ в CLAUDE.md).

## CRITICAL

### C1. Кнопки djoin / drebuy / dcashout пишут в ledger без проверок [✓] [×3]
- Где: `internal/delivery/telegram/commands.go:1188-1274` (вызовы `h.game.BuyIn/Rebuy/CashOut` на 1069, 1080, 1219); `internal/service/game.go:155-232`.
- Риск: проверяется только `game.DealerTgID == sender`. Нет проверки статуса игры, места игрока, повторного нажатия. `participants.Create` — upsert, так что повтор не падает. Двойной тап «Да» под `/dealer_cashout` → два CASH_OUT, банк в минусе. Кнопка под старым сообщением после `/endgame` → BUY_IN в ledger **завершённой** игры, расхождение с game_results.
- Действие: в колбэках вызывать `DealerBuyIn / DealerRebuy / DealerCashOut` (они проверяют `requireActiveDealer` и `IsActivePlayer`, работают в транзакции), ошибки ErrGameNotActive/ErrAlreadyInGame/ErrNotInGame отдавать текстом и убирать клавиатуру. Сырые `BuyIn/Rebuy/CashOut` сделать неэкспортируемыми.

### C2. Нет блокировок строк: check-then-act → двойные записи [✓] [×2]
- Где: `internal/service/table.go:87-138, 211-274, 323-389`; `FOR UPDATE` в проекте не используется нигде (grep пуст); изоляция Read Committed.
- Риск: два параллельных cash-out одного игрока (двойной тап в Mini App, бот + приложение) оба видят `is_active=true` → два CASH_OUT. Подтверждение JOIN в чате + «Посадить» в приложении → два BUY_IN.
- Действие: первым запросом каждой изменяющей транзакции стола — `SELECT … FROM games WHERE id=$1 FOR UPDATE`, перечитывать status/dealer внутри транзакции; `UPDATE participants SET is_active=false WHERE … AND is_active` с проверкой RowsAffected.

### C3. Завершение/отмена игры не атомарны, UPDATE без `status='active'` [×4]
- Где: `internal/service/table.go:422-470` (EndGame), `internal/service/game.go:99-125` (Finish), `internal/repository/postgres/game.go:173-175, 184-193`.
- Риск: участники, банк и ledger читаются вне транзакции Finish; `UPDATE games SET status='finished' WHERE id=$2` и Cancel не проверяют текущий статус. Параллельные /cancel и «Завершить» → finished-игра перезаписывается в cancelled при уже опубликованных settlements (или наоборот). BUY_IN, вклинившийся между чтением ledger и UPDATE, не попадает в game_results. Двойной «Завершить» → сырая 500 (PK game_results).
- Действие: весь EndGame (проверки, расчёт, вставки, CancelByGame) — в одной `InTx` с `FOR UPDATE` на games; `UPDATE … WHERE id=$1 AND status='active'`, при 0 строк → ErrGameNotActive. То же для Cancel. Проверять инвариант Σnet == −delta.

### C4. Доступ к группе в Mini App не отзывается никогда [✓]
- Где: `internal/delivery/http/api.go:168-184` (canSeeChat), `internal/service/table.go:662` (ForgetMember не вызывается нигде).
- Риск: попав в `chat_members` один раз, пользователь навсегда видит игры, участников и рейтинг группы, может создать игру в ней и отправлять join — даже если его выгнали.
- Действие: обрабатывать `chat_member` / `left_chat_member` апдейты → `ForgetMember`; при ответе getChatMember left/kicked — удалять; для createGame/join перепроверять членство через Telegram (кеш 5 мин уже есть) или хранить last_seen_at с TTL.

### C5. Токен Coolify уходит по HTTP на захардкоженный IP [✓]
- Где: `.github/workflows/ci.yml:69-71`.
- Риск: Bearer-токен с полным доступом к Coolify (деплой, env-секреты) передаётся без TLS при каждом push в master.
- Действие: HTTPS перед Coolify; URL/UUID в secrets; токен с минимальными правами. Токен после этого перевыпустить.
